## base

**What are Multipath Payments?** Multipath Payments (MPP) is a technique in the Lightning Network that splits a single payment into smaller partial payments, each routed through a different path to the same recipient. Instead of sending the entire amount through one route, the sender divides it into parts that travel independently across the network.

**The problem MPP solves.** Lightning payments are constrained by channel liquidity: a payment can only pass through a channel if the channel has enough capacity in the correct direction. Large payments often fail because no single path has sufficient liquidity end-to-end. MPP solves this by using multiple paths, each contributing a portion of the total amount.

**How it works.** The sender selects a set of routes whose combined capacity covers the payment amount. Each partial payment is wrapped in its own HTLC (Hash Time Locked Contract), but all share the same payment hash H(x). The receiver accumulates the partial HTLCs and only considers the payment complete when the sum of all received parts equals the expected amount. Because all parts share the same preimage x, the receiver releases the preimage only once — when the full amount has arrived.

**Key benefits.**

- **Reliability.** If one path has insufficient liquidity, the sender can retry that portion through a different route without restarting the entire payment.
- **Privacy.** Splitting a payment across multiple paths makes it harder for observers to determine the total amount being sent or the final destination.
- **Liquidity utilization.** MPP uses available liquidity across the network more efficiently, enabling larger payments than any single channel allows.

**Analogy.** Imagine carrying 200,000 sats in cash down a single street to reach your destination. If a roadblock stops you, the entire delivery fails. MPP is like splitting the cash into three envelopes sent via different streets. Even if one street is blocked, the other two arrive safely. The recipient confirms the delivery only when all envelopes are accounted for.

## medium

**The same payment hash constraint.** All partial payments in an MPP set must use the identical payment hash H(x). This constraint is fundamental to the security model: because all parts share the same preimage x, the recipient can only claim any given partial HTLC by revealing x. Once the full amount is received, the recipient reveals x once, and all partial HTLCs settle atomically. If a sender attempted to use different hashes per path, the recipient could claim each part independently without ever revealing a unifying proof of payment.

**How MPP support is signaled.** Both sender and receiver must advertise MPP support through feature bits in the Lightning protocol. The `basic_mpp` feature bit (bit 14 in BOLT 9) is negotiated during connection setup. If either party does not support MPP, the sender falls back to single-path payment. The feature bit is also encoded in BOLT 11 invoices via the `9` field, allowing the payer to know before paying whether the recipient supports MPP.

**The payment_secret mechanism.** BOLT 11 invoices include a `payment_secret` field — a random 32-byte value generated by the recipient. This secret serves two purposes:

1. **Binding partial payments together.** The payment_secret is included in each partial payment's onion payload. The receiver verifies that all incoming partial HTLCs carry the same payment_secret, confirming they belong to the same payment.

2. **Preventing preimage reuse attacks.** Without payment_secret, a malicious node could intercept a payment hash H(x) and create a new invoice claiming to be the original recipient. The payment_secret makes each payment unique, so observing H(x) on the network is insufficient to create a valid invoice.

**Path selection for partial payments.** Each partial payment is routed independently, potentially through completely different intermediate nodes. The sender's pathfinding algorithm:

1. Determines the total amount to send and the number of paths to use
2. Selects routes from sender to receiver that do not overlap in intermediate nodes (to avoid correlated failures)
3. Allocates amounts to each path based on available channel liquidity
4. Constructs a separate onion packet for each partial payment

The goal is to maximize the number of non-overlapping paths, reducing the risk that a single node failure disrupts multiple partial payments.

**MPP vs AMP (Atomic Multipath Payments).** MPP and AMP are two approaches to multipath payments with different trade-offs:

- **MPP (Base MPP).** All parts share one payment hash. The receiver waits for all parts. Simpler but requires the receiver to know the total amount in advance. Defined in BOLT 4 as part of the base protocol.
- **AMP (Atomic Multipath Payments).** Each partial payment has its own preimage. The recipient reconstructs the payment proof by combining all preimages. Benefits: does not require the total amount to be known upfront, enables "pay what you want" scenarios, and prevents a single node from blocking payment completion. Trade-off: more complex and not yet standardized across all implementations.

**The role of onions in MPP.** Each partial payment travels in its own onion-encrypted packet. The sender constructs N separate onions (one per path), each containing the partial amount and the `payment_secret` in the per-hop payload for the final recipient. Intermediate nodes cannot distinguish an MPP partial payment from a regular single-path payment — each onion looks like a normal payment to them.

## advanced

**The payment_secret in depth.** The `payment_secret` field is a cryptographic commitment that binds all partial payments of an MPP set together. When an invoice is generated, the recipient creates a random `payment_secret` and stores it. For each incoming HTLC, the recipient checks:

- The HTLC's onion payload contains a `payment_secret`
- The `payment_secret` matches the one from the invoice
- The total accumulated amount for that `payment_secret` does not exceed the invoice amount

This mechanism prevents several attacks. A probing node cannot send partial payments with a guessed `payment_secret` to learn whether a payment hash is active. The recipient rejects HTLCs with unknown or already-fulfilled `payment_secret` values at the protocol level, without revealing additional information.

**Onion routing with MPP.** Each partial payment gets its own complete onion packet, constructed exactly as a single-path payment would be. The sender builds a separate encrypted payload for each hop on each path. The only MPP-specific data is in the final hop's payload:

- `amt_to_forward`: the partial amount (not the total)
- `outgoing_cltv_value`: the CLTV for this partial payment
- `payment_secret`: binds this partial payment to the MPP set

Intermediate nodes process the onion as usual — peeling one layer, forwarding to the next hop. They have no visibility into whether the payment is part of an MPP set.

**Pathfinding optimization for MPP.** The sender's pathfinding algorithm for MPP is more complex than for single-path payments. Key considerations:

1. **Maximum split size.** Implementations typically limit MPP to a maximum number of partial payments (commonly 5-10) to avoid excessive routing fees and HTLC overhead.
2. **Minimum partial amount.** Very small partial payments waste fees. Most implementations set a floor (e.g., 1,000 sats) below which a part is not split further.
3. **Node disjointness.** Overlapping paths (sharing intermediate nodes) create correlated failure risk. Optimal path selection maximizes disjointness.
4. **Liquidity-aware splitting.** The sender estimates available liquidity on candidate channels and sizes partial payments accordingly. Channels nearing their capacity limit get smaller allocations.

The algorithm typically proceeds in rounds: find the best path, allocate as much as that path can carry, reduce the remaining amount, and repeat until the full amount is allocated or no more paths exist.

**Fee implications of splitting.** Splitting a payment increases total routing fees because more hops are involved. However, the per-path amount is smaller, which can reduce proportional fees on high-fee channels. The net effect depends on:

- The base fee per HTLC (fixed cost per partial payment)
- The fee rate of each channel used
- The number of additional hops introduced by splitting

Empirically, MPP adds 10-30% to total routing fees for large payments but dramatically improves success probability. For many applications, the reliability gain outweighs the fee increase.

**The receiver's perspective.** From the recipient's point of view, MPP introduces several considerations:

1. **HTLC accumulation.** The receiver's node must track incoming partial HTLCs grouped by `payment_secret`. Each partial HTLC is held in a pending state.
2. **Timeout handling.** Partial HTLCs have individual CLTV expiries. If a partial payment's timelock expires before others arrive, the receiver must decide whether to accept the incomplete set or wait for a retry.
3. **Partial payment failure recovery.** If some parts fail due to routing errors, the sender can retry those specific amounts along different paths. The receiver does not need to generate a new invoice — the existing `payment_secret` remains valid for retries.

Modern Lightning implementations (LND, CLN, Eclair) handle this automatically. The receiver simply generates an invoice and waits; the node software manages HTLC accumulation and fulfillment.

**AMP (Atomic Multipath Payments) in detail.** AMP extends the MPP concept by giving each partial payment its own preimage. When the sender constructs an AMP payment:

1. The sender generates N random preimages: x₁, x₂, ..., xₙ
2. Each preimage has its corresponding hash: H(x₁), H(x₂), ..., H(xₙ)
3. A "payment point" — a reconstruction secret — is split using Shamir's Secret Sharing so that any subset of K preimages (K ≤ N) can reconstruct the payment proof
4. The receiver claims each partial HTLC independently using the corresponding preimage
5. When enough preimages are collected, the receiver reconstructs the full payment proof

AMP's key advantage is that it removes the "all-or-nothing" constraint of MPP. The receiver can claim partial payments as they arrive, and the payment completes once a threshold number of parts succeed — even if some paths fail permanently.

However, AMP has not been adopted as a BOLT standard. LND implements it as a proprietary extension, while CLN relies on Base MPP. The community is working toward a unified specification.

**MPP in practice.** Real-world Lightning node implementations handle MPP automatically:

- **LND.** MPP is enabled by default. LND automatically probes paths and splits payments that exceed single-path capacity. It also supports AMP as an experimental feature.
- **CLN (Core Lightning).** Supports Base MPP with configurable splitting behavior. CLN's pathfinding algorithm (called the "Gossip Queries-based router") actively measures channel liquidity to inform split decisions.
- **Eclair (Scala).** Supports MPP with dynamic splitting controlled by the `multipart` flag. Eclair also implements trampoline routing, which can perform MPP splitting at the trampoline node.

When a user attempts a payment that exceeds any single path's capacity, their wallet automatically:

1. Generates an invoice request (if not already provided)
2. Identifies available paths using the network graph
3. Splits the payment across as many paths as needed
4. Monitors which parts succeed and which fail
5. Retries failed parts on alternative routes
6. Completes the payment once all parts arrive

**MPP and liquidity.** MPP fundamentally improves how the Lightning Network utilizes available liquidity. Consider a network where Alice wants to send 200,000 sats to Carol, but no single path has 200,000 sats in the right direction. Without MPP, the payment fails. With MPP, Alice can split across three paths using the combined capacity of multiple channels. This means the effective payment capacity of the network scales with the sum of all channel capacities in the routing graph, not just the largest individual path.

MPP also enables "liquidity aggregation across hops": a path that can only carry 80,000 sats between Alice and Bob and another path that can carry 70,000 sats between Bob and Carol can, through MPP, contribute to a single payment even though no single path connects all three.

**Scaling considerations.** As the Lightning Network grows, MPP becomes increasingly important for two reasons:

1. **Channel capacity distribution.** Most channels on the network are under 0.1 BTC. Large payments (>0.01 BTC) are nearly impossible to route through a single path. MPP makes large-value Lightning payments practical.
2. **Privacy under splitting.** Research suggests that splitting payments into many small parts makes statistical analysis techniques (like clustering payments to the same recipient) significantly harder. MPP provides a practical privacy benefit beyond what onion routing alone offers.

The trade-off is increased HTLC count on the network. Each partial payment creates an HTLC on every channel it traverses. High MPP usage increases the total number of pending HTLCs across the network, which can strain nodes with limited HTLC capacity. Implementations balance success probability against HTLC overhead when deciding how many splits to use.
